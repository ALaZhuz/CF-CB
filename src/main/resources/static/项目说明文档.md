# 项目说明文档

## 一句话总结

这是一个**"即时通知员"程序**：当 CodeBeamer 中的条目状态发生变化时，自动发送钉钉消息通知相关人员。

---

## 它具体在做什么？

想象这样一个场景：

```
CodeBeamer 条目状态变化：
    ┌─────────────────────┐
    │ 条目：需求A          │
    │ 状态：新建 → 处理中   │  ← 用户修改状态
    └─────────────────────┘
              ↓
      程序自动触发：
              ↓
    1. 校验：通知字段是否填写？userid是否有效？
    2. 通知：发钉钉消息给相关人员
    3. 记录：保存状态变化记录到数据库
```

**即时通知的完整工作流程**：

1. 用户在 CodeBeamer 修改条目状态
2. CodeBeamer 的 Groovy 脚本触发 → 调用本程序的校验接口
3. 校验成功 → 放行保存；校验失败 → 阻止保存并提示用户
4. 保存成功后 → Groovy 脚本触发 → 调用本程序的通知接口
5. 发送钉钉消息给相关人员
6. 记录状态变化到 SQLite 数据库

---

## 核心功能

### 1. beforeEvent 校验（保存前）

在条目保存前执行三项校验：
- 目标状态是否在工作流配置中显式声明
- 通知字段是否有成员填写
- 所有 userid 在钉钉中是否存在

**API**：`POST /workflow/validate`

### 2. afterEvent 通知（保存后）

在条目保存成功后，根据状态转换情况处理：

| previousState | targetState | 操作 |
|---------------|-------------|------|
| 通知状态 | 非通知状态 | 删除记录（离开状态） |
| 通知状态 | 通知状态 | 发送通知 + 更新记录（状态转换） |
| 非通知状态 | 通知状态 | 发送通知 + 插入记录（进入状态） |
| 非通知状态 | 非通知状态 | 无需处理 |

**API**：`POST /workflow/notify`

## 代码结构（简单版）

把它想象成一家餐厅：

```
App.java              → 餐厅大门（程序启动入口）

workflow/controller/  → 服务员（接待客人）
                      → 接收请求，把菜单给后厨

workflow/service/     → 后厨（做菜的地方）
                      → 真正干活的核心逻辑

workflow/config/      → 餐厅设置
                      → 工作流配置、通知规则等

workflow/cache/       → 仓库管理员
                      → 缓存 userid 有效性

db/                   → 仓库（数据库）
                      → SQLite 存储、Mapper 操作

service/              → 外部联络员
                      → 调用 CodeBeamer API、钉钉 API

model/                → 餐盘和菜单格式
                      → 数据长什么样（请求格式、返回格式）
```

## 配置文件说明

### application.yml（基础配置）

```yaml
codebeamer:
  base-url: https://cb-trial.hirain.com/cb/api  # CodeBeamer API地址
  username: yangyang.zhang                       # 登录用户名
  password: yangyang.zhang                       # 登录密码

ding:
  corp-id: xxx                   # 钉钉企业ID
  app-key: xxx                   # 钉钉应用Key
  app-secret: xxx                # 钉钉应用Secret
  agent-id: xxx                  # 钉钉AgentId
  mode: personal                 # 通知模式：enterprise或personal
  personal-webhook-url: xxx      # 个人钉钉Webhook（如使用personal模式）

sqlite:
  database-path: data/notification.db  # SQLite数据库路径

mybatis:
  type-handlers-package: org.example.db.config  # MyBatis类型处理器扫描路径
  configuration:
    map-underscore-to-camel-case: true  # 启用驼峰命名转换（target_state → targetState）

server:
  port: 8081                     # 本程序运行的端口
```

### workflow-config.yml（工作流通知配置）

```yaml
# Tracker类型映射（决定消息中 {trackertype} 显示内容）
type-mappings:
  global:
    Requirement: "需求"
    Bug: "缺陷"
    Task: "任务"
  projects:
    "5":
      Requirement: "智驾需求"      # 项目级覆盖全局

# 额外字段配置（三级优先级：tracker级 > 项目级 > 全局级）
extra-fields:
  global:
    - field: "priority"
      label: "优先级"
  projects:
    "5":
      - field: "customer"        # 项目级完全覆盖全局
        label: "客户"

# 全局工作流模板（无description字段）
global-workflows:
  - name: "标准Bug工作流"
    states:
      - name: "新建"
        notify: false
      - name: "处理中"
        notify-field: "assignedTo"
      - name: "已关闭"
        notify: false

# 项目级配置
projects:
  - project-id: 5
    workflows:
      - name: "智驾需求流程"
        states:
          - name: "评审中"
            notify-field: "assignedTo"
    # tracker-matching：tracker-id + tracker-type（无tracker-name）
    tracker-matching:
      - tracker-id: 5292
        workflow: "智驾需求流程"
      - tracker-type: "Bug"
        workflow: "标准Bug工作流"
    # trackers：差异部分配置（最高优先级）
    trackers:
      - tracker-id: 5292
        # tracker级 extra-fields（完全覆盖项目级）
        extra-fields:
          - field: "dueDate"
            label: "截止日期"
        states:
          - name: "评审中"
            notify-field: "评审人"
      - tracker-id: 5300
        # tracker级 extra-fields 空列表（不显示任何额外字段）
        extra-fields: []
```

**消息模板格式（固定）**：

```
【需求】
需求名称: 用户登录功能需求
需求状态: 评审中，请您处理
assignedTo: 张三,李四
截止日期: 2025-06-30           ← tracker级extra-fields
需求链接: https://cb.example.com/item/12345
```

**extra-fields 说明**：
- 配置的 `field` 名称必须与 Codebeamer API 返回的 `customFields` 中的 `name` 一致
- 如果配置的字段在 Codebeamer 中不存在，会打印警告日志提示
- 支持的字段类型：成员类型（显示名称列表）、文本、日期、选择等

## 运行 App.java 时的完整启动流程

当你运行 `App.java` 时，Spring Boot 会依次执行以下步骤：

### 第一步：App.java 启动

```
文件：src/main/java/org/example/App.java
函数：main(String[] args)
作用：程序入口，启动 Spring Boot 容器

调用：SpringApplication.run(App.class, args)
      → Spring Boot 开始扫描并创建所有组件
```

### 第二步：加载配置文件

```
文件：src/main/resources/application.yml
作用：读取基础配置（CodeBeamer地址、钉钉配置、数据库路径等）

文件：src/main/resources/workflow-config.yml
作用：读取工作流通知配置（四层优先级、状态规则、消息模板等）

绑定到：
  - CBProperties.java（CodeBeamer配置）
  - DingProperties.java（钉钉配置）
  - WorkflowProperties.java（工作流配置）
```

### 第三步：创建数据库

```
文件：src/main/java/org/example/db/config/SQLiteConfig.java
函数：sqliteDataSource()
作用：
  1. 创建数据库目录（data/）
  2. 连接 SQLite 数据库文件（notification.db）
  3. 启用 WAL 模式（支持并发读写）
  4. 设置 busy_timeout（锁定时等待30秒）
  5. 执行建表语句，创建两张表：
     - item_state_record（状态记录表）
     - notify_log（发送日志表）

文件：src/main/java/org/example/db/config/SQLiteLocalDateTimeTypeHandler.java
作用：
  - 将 Java LocalDateTime 转换为 SQLite TEXT 格式
  - 存储格式：yyyy-MM-dd HH:mm:ss

调用：initDatabase(dataSource)
      → 执行 PRAGMA journal_mode=WAL
      → 执行 PRAGMA busy_timeout=30000
      → 执行 CREATE TABLE IF NOT EXISTS 语句
```

### 第四步：创建缓存服务并初始化

```
文件：src/main/java/org/example/workflow/cache/DingUserCacheService.java
函数：initCache()（@PostConstruct 标记，容器创建实例后自动执行）
作用：
  1. 调用 CBSwaggerService.getAllUsers() 获取 CodeBeamer 所有用户
  2. 对每个用户调用 DingService.checkUserExists() 验证钉钉存在性
  3. 将存在的 userid 存入内存缓存 Set（validUserIds）

调用链：
  initCache()
    → refreshCache()
      → cbSwaggerService.getAllUsers()
        → 调用 CodeBeamer API: /v3/users
      → dingService.checkUserExists(userid)
        → 调用钉钉 API 验证用户存在性
      → validUserIds.add(userid)
```

### 第五步：创建其他服务组件

```
Spring Boot 自动创建以下服务实例（通过依赖注入）：

1. WorkflowConfigService
   文件：src/main/java/org/example/workflow/config/WorkflowConfigService.java
   作用：查询工作流配置，实现四层优先级逻辑

2. WorkflowValidateService
   文件：src/main/java/org/example/workflow/service/WorkflowValidateService.java
   作用：beforeEvent 校验逻辑

3. WorkflowNotifyService
   文件：src/main/java/org/example/workflow/service/WorkflowNotifyService.java
   作用：afterEvent 通知逻辑

4. CBSwaggerServiceImpl
   文件：src/main/java/org/example/service/impl/CBSwaggerServiceImpl.java
   作用：调用 CodeBeamer API

5. DingServiceImpl
   文件：src/main/java/org/example/service/impl/DingServiceImpl.java
   作用：调用钉钉 API 发送消息

6. ItemStateRecordMapper、NotifyLogMapper
   文件：src/main/java/org/example/db/mapper/
   作用：SQLite 数据库操作（插入、删除、查询）
```

### 第六步：创建控制器

```
Spring Boot 自动创建控制器实例，绑定 HTTP 路径：

1. WorkflowValidateController
   文件：src/main/java/org/example/workflow/controller/WorkflowValidateController.java
   路径：POST /workflow/validate
   作用：接收 beforeEvent 校验请求

2. WorkflowNotifyController
   文件：src/main/java/org/example/workflow/controller/WorkflowNotifyController.java
   路径：POST /workflow/notify
   作用：接收 afterEvent 通知请求
```

### 第七步：启动定时任务

```
文件：src/main/java/org/example/workflow/cache/DingUserCacheService.java
函数：scheduledRefresh()（@Scheduled(fixedRate = 3600000) 标记）
作用：每小时自动刷新 userid 缓存
      → 重新调用 refreshCache() 验证所有用户
```

### 第八步：启动完成

```
控制台输出：============项目成功启动!============
服务运行在：http://localhost:8081
等待接收：CodeBeamer Groovy 脚本的 HTTP 请求
```

## 收到请求时的处理流程

### 收到校验请求（/workflow/validate）

```
┌─────────────────────────────────────────────────────────────┐
│  CodeBeamer Groovy 脚本发送请求                              │
│  POST /workflow/validate                                     │
│  Body: { itemId: 12345, targetState: "处理中" }              │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  WorkflowValidateController.validate()                       │
│  → 接收请求，调用 WorkflowValidateService.validate()         │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  WorkflowValidateService.validate()                          │
│  → cbSwaggerService.getItemInfo(itemId)                      │
│      → HTTP: CodeBeamer /v3/items/{itemId}                   │
│      → 获取条目详情（tracker信息、项目信息、成员字段）         │
│  → workflowConfigService.getWorkflowForTracker()             │
│      → 查找四层优先级配置                                     │
│  → workflowConfigService.isStateDeclared()                   │
│      → 判断目标状态是否已声明                                 │
│  → workflowConfigService.shouldNotify()                      │
│      → 判断是否需要通知                                       │
│  → dingUserCacheService.findInvalidUserIds()                 │
│      → 检查 userid 有效性                                     │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  返回校验结果                                                 │
│  { success: true/false, errorMessage: "..." }               │
│  → CodeBeamer 根据结果决定是否放行保存                        │
└─────────────────────────────────────────────────────────────┘
```

### 收到通知请求（/workflow/notify）

```
┌─────────────────────────────────────────────────────────────┐
│  CodeBeamer Groovy 脚本发送请求                              │
│  POST /workflow/notify                                       │
│  Body: { itemId: 12345, previousState: "新建",               │
│          targetState: "处理中" }                              │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  WorkflowNotifyController.notify()                           │
│  → 接收请求，调用 WorkflowNotifyService.notify()             │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  WorkflowNotifyService.notify()                              │
│  → cbSwaggerService.getItemInfo(itemId)                      │
│      → HTTP: CodeBeamer /v3/items/{itemId}                   │
│  → workflowConfigService.getStateConfig(previousState)       │
│      → 判断 previousState 是否需要通知                        │
│  → workflowConfigService.getStateConfig(targetState)         │
│      → 判断 targetState 是否需要通知                          │
│  → 状态转换决策：                                             │
│      - previousState通知 + targetState不通知 → 删除记录       │
│      - previousState通知 + targetState通知 → 发送通知+更新    │
│      - previousState不通知 + targetState通知 → 发送通知+插入  │
│      - 都不通知 → 无需处理                                    │
│  → dingService.sendTextMessage(userid, content)              │
│      → HTTP: 钉钉消息发送API                                  │
│  → notifyLogMapper.insert()                                  │
│      → 写入 SQLite：表2 发送日志                              │
│  → itemStateRecordMapper.insert()                            │
│      → 写入 SQLite：表1 状态记录（INSERT OR REPLACE）         │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  返回通知结果                                                 │
│  { success: true, notifiedUsers: ["123", "456"],             │
│    actionType: "进入状态" }                                   │
└─────────────────────────────────────────────────────────────┘
```
