# 项目说明文档

## 一句话总结

这是一个**"即时通知员"程序**：当 CodeBeamer 中的条目状态发生变化时，自动发送钉钉消息通知相关人员。

---

## 它具体在做什么？

想象这样一个场景：

```
CodeBeamer 条目状态变化：
    ┌─────────────────────┐
    │ 条目：需求A          │
    │ 状态：新建 → 处理中   │  ← 用户修改状态
    └─────────────────────┘
              ↓
      程序自动触发：
              ↓
    1. 校验：通知字段是否填写？userid是否有效？
    2. 通知：发钉钉消息给相关人员
    3. 记录：保存状态变化记录到数据库
```

**即时通知的完整工作流程**：

1. 用户在 CodeBeamer 修改条目状态
2. CodeBeamer 的 Groovy 脚本触发 → 调用本程序的校验接口
3. 校验成功 → 放行保存；校验失败 → 阻止保存并提示用户
4. 保存成功后 → Groovy 脚本触发 → 调用本程序的通知接口
5. 发送钉钉消息给相关人员
6. 记录状态变化到 SQLite 数据库

---

## 核心功能

### 1. beforeEvent 校验（保存前）

在条目保存前执行三项校验：
- 目标状态是否在工作流配置中显式声明
- 通知字段是否有成员填写
- 所有 userid 在钉钉中是否存在

**API**：`POST /workflow/validate`

### 2. afterEvent 通知（保存后）

在条目保存成功后，根据状态转换情况处理：

| previousState | targetState | 操作 |
|---------------|-------------|------|
| 通知状态 | 非通知状态 | 删除记录（离开状态） |
| 通知状态 | 通知状态 | 发送通知 + 更新记录（状态转换） |
| 非通知状态 | 通知状态 | 发送通知 + 插入记录（进入状态） |
| 非通知状态 | 非通知状态 | 无需处理 |

**API**：`POST /workflow/notify`

### 3. 定时通知（每日提醒）

每天指定时间扫描停留在通知状态的条目，发送分级提醒通知：

| 通知层级 | 发送规则 | 聚合方式 |
|---------|---------|---------|
| 成员通知 | 每隔 N 天发送一次（周期性） | 逐人发送 |
| 科长通知 | 达到阈值后**每天发送** | **跨条目聚合**（一条消息包含所有负责条目） |
| 部长通知 | 达到阈值后**每天发送** | **跨条目聚合** |

**触发条件**：
1. 状态配置了 `scheduled-notify: true`
2. 条目在 `classify-config` 中匹配到分类规则
3. 停留天数达到对应层级的阈值

**执行时间**：由根级 `default-notify-time` 配置决定（如 "21:30"）

**关键依赖**：
- **classify-config**：分类通知配置，决定不同优先级的升级天数
  - `classify-field`：分类字段（如 priority）
  - `classify-rules`：分类规则，包含升级天数配置
- **OrgCacheService**：组织架构缓存，用于查找成员的科长、部长

**特殊场景处理**：
- 条目负责人【A, B】→ A的科长是C，B的科长是D → C和D都会收到包含该条目的消息
- 聚合时使用 Set 去重，同一条目不会重复出现在科长/部长的消息中
- 消息开头动态调整："以下需求未及时处理"、"以下Bug未及时处理"等
- 发送失败的条目不更新 last_notify_time，下次执行时自动重试
- 遇到 API 速率限制（429）时自动等待重试

**配置热更新**：
- 启动时强制从 YAML 同步配置到数据库和内存
- 运行时检测 YAML 变更自动重新加载配置
- 支持手动调用 `/admin/config/reload` 热更新

**组织架构缓存管理**：
- OrgCacheService 使用 `ReviewService.queryOrganizationManager()` 获取科长/部长信息
- 每小时自动刷新组织架构缓存
- 组织架构变化时可手动调用 `/admin/org-cache/refresh` 强制刷新

---

### 4. 管理接口

提供手动触发运维操作的接口（均在 `ScheduledNotifyController` 中定义）：

| 接口 | 方法 | 作用 |
|------|------|------|
| `/admin/org-cache/refresh` | POST | 手动刷新组织架构缓存 |
| `/admin/config/reload` | POST | 手动重新加载 YAML 配置 |
| `/admin/init` | POST | 手动触发全量初始化 |
| `/admin/supplement/{projectId}` | POST | 按项目补录存量条目 |
| `/admin/status` | GET | 查询当前状态 |

#### 接口详细说明

**1. 刷新组织架构缓存**
```
POST /admin/org-cache/refresh
```
返回：
```json
{
  "success": true,
  "cacheSize": 100,
  "message": "组织架构缓存已刷新"
}
```
场景：组织架构变化（科长/部长调整）时调用

**2. 重加载配置**
```
POST /admin/config/reload
```
返回：
```json
{
  "success": true,
  "message": "配置已重新加载，yaml_content已更新"
}
```
场景：修改 workflow-config.yml 后立即生效

**3. 手动全量初始化**
```
POST /admin/init
```
返回：
```json
{
  "success": true,
  "message": "全量初始化已触发"
}
```
场景：重置初始化状态并重新扫描所有存量条目

**4. 按项目补录**
```
POST /admin/supplement/{projectId}
```
返回：
```json
{
  "success": true,
  "projectId": 5,
  "processed": 50,
  "inserted": 30,
  "skipped": 20,
  "message": "补录完成，处理50条，新增30条，跳过20条"
}
```
场景：新增项目或新增 tracker 配置后补录存量数据

**5. 查询状态**
```
GET /admin/status
```
返回：
```json
{
  "initialized": true,
  "orgCacheSize": 100
}
```
场景：检查系统初始化状态和缓存大小

## 代码结构（简单版）

把它想象成一家餐厅：

```
App.java              → 餐厅大门（程序启动入口）

workflow/controller/  → 服务员（接待客人）
                      → 接收请求，把菜单给后厨

workflow/service/     → 后厨（做菜的地方）
                      → 真正干活的核心逻辑

workflow/config/      → 餐厅设置
                      → 工作流配置、通知规则等

workflow/cache/       → 仓库管理员
                      → 缓存 userid 有效性、组织架构

workflow/service/     → 初始化服务
                      → 全量扫描、按项目补录

db/                   → 仓库（数据库）
                      → SQLite 存储、Mapper 操作

service/              → 外部联络员
                      → 调用 CodeBeamer API、钉钉 API

model/                → 餐盘和菜单格式
                      → 数据长什么样（请求格式、返回格式）
```

### workflow-config.yml（工作流通知配置）

```yaml
# 根级配置
default-notify-time: "21:30"        # 定时通知执行时间（格式：HH:mm）

# 钉钉通知模式
dingtalk:
  mode: enterprise                   # enterprise（企业钉钉）或 personal（个人钉钉Webhook）

# 分类通知配置（定时通知功能）
classify-config:
  projects:
    "5":                             # 项目ID
      tracker-types:
        "Bug":                       # Bug 类型启用分类通知
          classify-field: "priority" # 分类字段
          classify-rules:
            - category: "High"       # 高优先级
              member-interval-days: 1      # 成员每1天通知
              manager-escalate-days: 3     # 停留3天后通知科长
              director-escalate-days: 5    # 停留5天后通知部长
            - category: "Normal"
              member-interval-days: 1
              manager-escalate-days: 5
              director-escalate-days: null # 不通知部长
        "Requirement": null          # Requirement 类型不启用分类通知

# Tracker类型映射（决定消息中 {trackertype} 显示内容）
type-mappings:
  global:
    Requirement: "需求"
    Bug: "缺陷"
    Task: "任务"
  projects:
    "5":
      Requirement: "智驾需求"      # 项目级覆盖全局

# 额外字段配置（三级优先级：tracker级 > 项目级 > 全局级）
extra-fields:
  global:
    - field: "priority"
      label: "优先级"
  projects:
    "5":
      - field: "customer"        # 项目级完全覆盖全局
        label: "客户"

# 全局工作流模板（无description字段）
global-workflows:
  - name: "标准Bug工作流"
    states:
      - name: "新建"
        notify: false
      - name: "处理中"
        notify-field: "assignedTo"
        scheduled-notify: true   # 启用定时通知
      - name: "已关闭"
        notify: false

# 项目级配置
projects:
  - project-id: 5
    workflows:
      - name: "智驾需求流程"
        states:
          - name: "评审中"
            notify-field: "assignedTo"
            scheduled-notify: true  # 启用定时通知
    # tracker-matching：tracker-id + tracker-type（无tracker-name）
    tracker-matching:
      - tracker-id: 5292
        workflow: "智驾需求流程"
      - tracker-type: "Bug"
        workflow: "标准Bug工作流"
    # trackers：差异部分配置（最高优先级）
    trackers:
      - tracker-id: 5292
        # tracker级 extra-fields（完全覆盖项目级）
        extra-fields:
          - field: "dueDate"
            label: "截止日期"
        states:
          - name: "评审中"
            notify-field: "评审人"
      - tracker-id: 5300
        # tracker级 extra-fields 空列表（不显示任何额外字段）
        extra-fields: []
```

**消息模板格式（固定）**：

```
【需求】
需求名称: 用户登录功能需求
需求状态: 评审中，请您处理
assignedTo: 张三,李四
截止日期: 2025-06-30           ← tracker级extra-fields
需求链接: https://cb.example.com/item/12345
```

**extra-fields 说明**：
- 配置的 `field` 名称必须与 Codebeamer API 返回的 `customFields` 中的 `name` 一致
- 如果配置的字段在 Codebeamer 中不存在，会打印警告日志提示
- 支持的字段类型：成员类型（显示名称列表）、文本、日期、选择等

## 运行 App.java 时的完整启动流程

当你运行 `App.java` 时，Spring Boot 会依次执行以下步骤：

### 第一步：App.java 启动

```
文件：src/main/java/org/example/App.java
函数：main(String[] args)
作用：程序入口，启动 Spring Boot 容器

调用：SpringApplication.run(App.class, args)
      → Spring Boot 开始扫描并创建所有组件
```

### 第二步：加载配置文件

```
文件：src/main/resources/application.yml
作用：读取基础配置（CodeBeamer地址、钉钉配置、数据库路径等）

文件：src/main/resources/workflow-config.yml
作用：读取工作流通知配置（四层优先级、状态规则、消息模板等）

绑定到：
  - CBProperties.java（CodeBeamer配置）
  - DingProperties.java（钉钉配置）
  - WorkflowProperties.java（工作流配置）
```

### 第三步：创建数据库

```
文件：src/main/java/org/example/db/config/SQLiteConfig.java
函数：sqliteDataSource()
作用：
  1. 创建数据库目录（data/）
  2. 连接 SQLite 数据库文件（notification.db）
  3. 启用 WAL 模式（支持并发读写）
  4. 设置 busy_timeout（锁定时等待30秒）
  5. 执行建表语句，创建两张表：
     - item_state_record（状态记录表）
     - notify_log（发送日志表）

文件：src/main/java/org/example/db/config/SQLiteLocalDateTimeTypeHandler.java
作用：
  - 将 Java LocalDateTime 转换为 SQLite TEXT 格式
  - 存储格式：yyyy-MM-dd HH:mm:ss

调用：initDatabase(dataSource)
      → 执行 PRAGMA journal_mode=WAL
      → 执行 PRAGMA busy_timeout=30000
      → 执行 CREATE TABLE IF NOT EXISTS 语句
```

### 第四步：创建缓存服务并初始化

```
文件：src/main/java/org/example/workflow/cache/DingUserCacheService.java
函数：initCache()（@PostConstruct 标记，容器创建实例后自动执行）
作用：
  1. 调用 CBSwaggerService.getAllUsers() 获取 CodeBeamer 所有用户
  2. 对每个用户调用 DingService.checkUserExists() 验证钉钉存在性
  3. 将存在的 userid 存入内存缓存 Set（validUserIds）

文件：src/main/java/org/example/workflow/cache/OrgCacheService.java

  1. 调用钉钉 API 获取组织架构信息

```
```
┌─────────────────────────────────────────────────────────────┐
```

```
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  检查缓存就绪状态                                             │
│  → orgCacheService.getCacheSize() > 0                       │
│  → dingUserCacheService.getCacheSize() > 0                  │
│  → 未就绪 → 跳过本次执行                                      │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  检查配置变更                                                 │
│  → configMetaService.checkYamlModified()                    │
│  → 有变更 → configMetaService.reloadYamlConfig() 热更新     │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  查询待通知条目                                               │
│  → itemStateRecordMapper.selectAll()                        │
│  → 过滤：last_notify_time 不是今天的条目                     │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  收集通知数据（buildNotifyData）                              │
│  → 获取条目信息、trackerType、workflow 配置                  │
│  → 检查状态是否启用 scheduled-notify                         │
│  → 计算 stayDays（停留天数）                                  │
│  → 获取 classify-config 分类配置                             │
│  → 匹配 classifyRule（根据 priority 字段值）                  │
│  → 获取通知字段成员并验证 userid 有效性                       │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  发送成员通知（周期性）                                       │
│  → 判断：stayDays >= interval && stayDays % interval == 0   │
│  → 逐人发送钉钉消息                                           │
│  → 记录 notify_log                                           │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  发送科长通知（跨条目聚合）                                   │
│  → 判断：stayDays >= manager-escalate-days                   │
│  → 按 科长userid 聚合条目列表                                │
│  → 使用 Set 去重：同一条目不会重复出现                        │
│  → orgCacheService.getManager(member.userid) 获取科长       │
│  → 每个科长收到一条包含所有负责条目的消息                     │
│  → 消息开头动态调整："以下需求/以下Bug/以下问题..."           │
│  → 记录 notify_log（成功和失败都记录）                        │
│  → 发送成功：标记条目为已通知                                 │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  发送部长通知（跨条目聚合）                                   │
│  → 判断：stayDays >= director-escalate-days                  │
│  → 按 部长userid 聚合条目列表                                │
│  → 使用 Set 去重：同一条目不会重复出现                        │
│  → orgCacheService.getDirector(member.userid) 获取部长      │
│  → 每个部长收到一条包含所有负责条目的消息                     │
│  → 消息开头动态调整："以下需求/以下Bug/以下问题..."           │
│  → 记录 notify_log（成功和失败都记录）                        │
│  → 发送成功：标记条目为已通知                                 │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│  更新条目记录（仅发送成功的条目）                             │
│  → 只更新发送成功的条目的 last_notify_time                   │
│  → 发送失败的条目下次执行时会重试                             │
│  → 输出统计：成员通知数、科长通知数、部长通知数                │
└─────────────────────────────────────────────────────────────┘
```
